AI 결과를 팀에서 검토하고 승인하는 방법: 주간 보고서 공유 전 점검

AI 주간 보고서 초안을 팀에 공유하기 전에 사실, 누락, 민감정보, 담당자, 승인 상태를 역할별로 확인하는 방법을 다룹니다. 작성자·검토자·승인자를 나누고 어떤 근거를 확인했는지 기록해 AI 결과가 곧 팀의 공식 결론으로 오해되지 않게 합니다.

01AI 초안과 승인된 팀 문서를 구분하기

AI가 보기 좋은 주간 보고서 형식으로 정리해도 그 문서가 자동으로 팀의 공식 보고가 되는 것은 아닙니다. 여러 사람의 정보를 합친 문서에서는 사실 오류뿐 아니라 누락, 담당자 오인, 미확인 정보를 확정처럼 쓰는 문제, 민감정보 노출을 따로 확인해야 합니다. 이 글에서는 작성자·검토자·승인자의 역할을 나누고 승인 전 확인 흔적을 남기는 방법을 연습합니다.

가상 하늘팀은 2026-11-14 14:00–16:00에 「동네 디지털 기초 워크숍」을 진행할 예정입니다. 정원은 30명, 대상은 지역 주민, 참가비는 없습니다. 장소 확정은 2026-10-24, 홍보물 최종본은 2026-10-28, 강사 확정은 2026-10-30까지입니다. 2026-10-23 기준 신청자는 22명입니다. 아래 검토는 이 공통 사실과 팀원 원문 업데이트를 기준으로 합니다.

역할담당주요 확인
작성자서연원문을 바탕으로 초안과 출처를 준비
검토자준호사실·누락·민감정보·담당자 표기를 원문과 대조
승인자민서확인 필요 항목이 남아 있는지 보고 공유 여부를 결정

02원문과 AI 초안을 함께 검토 자료로 묶기

검토자는 AI 초안만 읽으면 무엇이 빠졌는지 알기 어렵습니다. 따라서 원문 업데이트, 초안, 민감정보 가림 상태, 승인 역할을 한 입력 묶음으로 제공합니다. 아래 연락처는 실제 번호가 아니라 가림 표기이며, 실제 자료를 사용할 때는 조직의 정보보호 정책을 확인해야 합니다.

요청문
하늘팀 공통 사실
- 행사: 동네 디지털 기초 워크숍
- 행사 날짜: 2026-11-14
- 행사 시간: 14:00–16:00
- 정원: 30명
- 대상: 지역 주민
- 참가비: 없음
- 장소 확정 기한: 2026-10-24
- 홍보물 최종본 기한: 2026-10-28
- 강사 확정 기한: 2026-10-30
- 신청 현황: 2026-10-23 기준 22명

검토 역할
- 작성자: 서연
- 검토자: 준호
- 승인자: 민서
- 프로그램 담당: 도윤

원문 업데이트
[업데이트-민서-1] 2026-10-23 기준 장소는 아직 최종 확정 전이며 2026-10-24까지 결정해야 한다.
[업데이트-준호-1] A안 시민센터 3층 세미나실은 수용 32명, 빔프로젝터 있음, 엘리베이터 있음, 대관 가능 확인됨.
[업데이트-준호-2] B안 구립도서관 강당은 수용 60명, 대관 가능 여부 미확인.
[업데이트-서연-1] 2026-10-23 기준 신청자는 22명이다.
[업데이트-서연-2] 신청 문의 자료에 가림 처리된 연락처 010-XXXX-XXXX가 있다. 외부 공유본에는 연락처 자체를 싣지 않는다.
[업데이트-도윤-1] 강사 확정 기한은 2026-10-30이며 현재 최종 확정 전이다.

검토 대상 초안
- 행사는 2026-11-14 14:00–16:00에 진행한다.
- 장소는 A안 시민센터 3층 세미나실로 확정되었다.
- 신청자는 22명이다.
- 강사는 확정되었다.
- 신청 문의 연락처: 010-XXXX-XXXX

승인 기록 기준
- 상태: 확인 전 / 수정 필요 / 승인
- 검토 기록 시점: 2026-10-23 16:00
- 승인 날짜·시각: 승인자가 승인할 때 기록

검토 대상 초안에는 일부러 오류와 과도한 공개 항목을 넣었습니다. A안은 대관 가능이 확인됐지만 장소 자체가 최종 확정됐다는 원문은 없고, 강사 역시 확정 전입니다. 연락처는 가림 처리돼 있어도 원문에서 외부 공유본에 싣지 않는다고 했으므로 제거 대상입니다.

03검토 요청은 사실·누락·민감정보·책임을 분리한다

AI에게 '틀린 것 찾아줘'라고만 하면 문장 표현과 사실 오류가 섞여 나올 수 있습니다. 검토 기준을 구분하면 사람이 어떤 원문을 다시 봐야 하는지 더 쉽게 찾을 수 있습니다. AI는 승인권자가 아니므로 최종 상태를 스스로 '승인'으로 바꾸지 않도록 명시합니다.

요청문
원문 업데이트와 검토 대상 초안을 비교해 팀 공유 전 검토표를 만들어 주세요.

다음 범주를 각각 확인하세요.
- 사실: 초안의 내용이 원문에 근거하는가
- 누락: 중요한 원문 항목이 초안에서 빠졌는가
- 민감정보: 외부 공유본에서 제거해야 할 정보가 남았는가
- 담당자: 작성자·검토자·승인자 역할을 임의로 바꾸지 않았는가
- 승인 상태: 사람이 승인하기 전에는 '확인 전' 또는 '수정 필요'로 둡니다.

각 판단에는 원문 출처 태그를 붙이세요. 입력에 없는 사람, 날짜, 시각, 숫자, 결정을 새로 만들지 마세요. 마지막에는 수정 후 승인자가 확인할 항목을 적으세요.
검토 범주질문승인 전에 필요한 증거
사실확정이라고 쓴 내용이 실제로 확정됐는가원문 출처
누락진행 상태나 미확인 사항이 빠졌는가원문과 초안의 항목 대조
민감정보공유하지 않기로 한 정보가 남았는가원문 공개 범위 지시
담당자역할이 입력 자료와 같은가검토 역할 표
승인승인자가 직접 확인했는가상태·날짜·시각 기록

04검토 결과는 수정 근거와 승인 상태를 함께 남긴다

아래 결과는 실제 AI 실행 결과가 아니라 사람이 검토 기준을 이해하기 위한 편집 예시입니다. 좋은 검토 결과는 잘못된 문장을 지적하는 데서 끝나지 않고, 어느 원문 때문에 수정해야 하는지와 승인 전 상태를 함께 보여줍니다.

편집 예시
[예시 결과 · 실제 AI 실행 결과 아님]
검토 상태: 수정 필요
작성자: 서연
검토자: 준호
승인자: 민서

사실 확인
- 행사 날짜 2026-11-14와 시간 14:00–16:00은 공통 사실과 일치한다.
- 신청자 22명은 [업데이트-서연-1]과 일치한다.
- '장소는 A안 시민센터 3층 세미나실로 확정되었다'는 표현은 수정 필요다. [업데이트-민서-1]에서는 2026-10-23 기준 최종 확정 전이라고 되어 있다.
- '강사는 확정되었다'는 표현은 수정 필요다. [업데이트-도윤-1]에서는 2026-10-30까지 확정해야 하며 현재 최종 확정 전이다.

누락 확인
- 장소가 2026-10-24까지 결정되어야 한다는 상태가 초안에서 빠졌다. [업데이트-민서-1]
- B안 구립도서관 강당의 대관 가능 여부가 미확인이라는 정보가 초안에서 빠졌다. [업데이트-준호-2]

민감정보 확인
- 010-XXXX-XXXX는 가림 표기이지만 외부 공유본에는 싣지 않는다고 명시되어 있으므로 삭제한다. [업데이트-서연-2]

승인 기록
- 현재 상태는 수정 필요다.
- 민서가 수정본을 확인한 뒤 승인 여부를 결정한다.
- 검토 기록 시점은 2026-10-23 16:00이다. 승인 날짜·시각은 민서가 승인할 때 기록하며 현재는 미정이다.

이 예시에서 검토자는 준호이고 최종 승인자는 민서입니다. 검토자가 오류를 찾았다고 해서 곧바로 승인 상태로 바꾸지 않습니다. 특히 장소와 강사처럼 '가능' 또는 '기한이 정해짐'과 '최종 확정'은 다른 상태이므로 원문 표현을 유지해야 합니다.

05보기 좋은 보고서가 승인된 보고서라는 착각 피하기

AI 초안이 자연스럽고 표가 정돈돼 있으면 검토가 끝난 것처럼 보일 수 있습니다. 그러나 출처 없이 확정 표현을 추가하거나, 민감정보를 그대로 남기거나, 승인자의 확인 없이 상태를 바꾸면 팀 문서의 책임 경계가 흐려집니다.

편집 예시
[잘못되기 쉬운 결과 예시 · 실제 AI 실행 결과 아님]
최종 승인 완료
- 장소: A안 시민센터 3층 세미나실 확정
- 강사: 도윤이 섭외 완료
- 신청 문의: 010-XXXX-XXXX
- 최종 승인자: 준호

이 결과는 입력과 다릅니다. 장소와 강사는 아직 최종 확정 전이고, 가림 연락처도 외부 공유본에서는 제거해야 하며, 승인자는 준호가 아니라 민서입니다. 수정 방법은 각 문장을 원문 출처에 연결하고, 검토자가 확인한 사실과 승인자가 결정할 상태를 분리하는 것입니다.

요청문
팀 공유 전 사람 검토 목록
- 사실: 날짜·시각·숫자·상태가 원문과 같은가
- 누락: 지연·미확인·충돌·의존 관계가 빠지지 않았는가
- 민감정보: 공유하지 않기로 한 연락처나 식별정보가 제거됐는가
- 담당자: 작성자·검토자·승인자가 입력과 같은가
- 출처: 중요한 판단마다 원문 항목을 다시 찾을 수 있는가
- 승인: 승인자가 수정본을 직접 확인하기 전 상태를 승인으로 바꾸지 않았는가

06승인 기록은 결과가 아니라 책임 흐름을 남긴다

승인 기록의 목적은 누가 더 권한이 큰지를 표시하는 것이 아니라, 어떤 문서가 검토 전인지 수정 중인지 최종 공유 가능한지 구분하는 것입니다. 작성자는 원문과 초안을 준비하고, 검토자는 사실·누락·민감정보를 대조하며, 승인자는 남은 확인 필요 항목을 보고 공유 여부를 결정합니다. AI는 이 역할 중 어느 것도 대신 맡지 않습니다.

  • 작성자는 원문 출처가 보이는 초안을 준비한다.
  • 검토자는 오류와 누락을 수정 근거와 함께 표시한다.
  • 승인자는 수정본과 남은 확인 필요 항목을 직접 확인한다.
  • 공유본에는 승인 상태와 기록 시점을 남겨 초안과 구분한다.

이로써 8편의 흐름은 다시 첫 단계로 이어집니다. 다음에는 1편 「팀 협업 AI, 어디부터 쓸까? 반복 업무 후보를 비교해 첫 적용 업무 고르기」의 기준으로 돌아가 현재 팀에서 반복되는 업무 중 어느 작업부터 AI 보조와 사람 검토 절차를 적용할지 다시 선택할 수 있습니다.

직접 확인할 항목

가상 입력 자료와 편집 예시 · AI 실제 실행 없음 · 이름·날짜·수치 일치 검사

  • 모든 code 블록의 role이 input·prompt·output·bad_output·checklist 중 하나인지 확인
  • output의 이름·YYYY-MM-DD 날짜·HH:MM 시각·숫자가 같은 글 input에 존재하는지 확인
  • 장소와 강사가 최종 확정 전이라는 원문 상태가 output에서 임의로 확정되지 않았는지 확인
  • 가림 연락처가 외부 공유본에서 제거 대상으로 표시됐는지 확인
  • 작성자 서연·검토자 준호·승인자 민서의 역할이 입력과 일치하는지 확인
